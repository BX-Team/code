# Pulsify — Analytics Platform (bstats alternative)

## Overview

Analytics platform Pulsify for Minecraft servers and plugins. Similar to bstats.org but with more features (error logging, custom metrics and etc.).
Servers/plugins/mods send data via Java SDK → Ingest API → Queue → Worker → Storage → Frontend.

---

## Tech Stack

| Layer | Technology |
|---|---|
| Frontend | Nuxt 4, TypeScript, Better Auth, Drizzle ORM, shadcn-vue |
| Ingest API | Hono, TypeScript |
| Worker | BullMQ, Node.js, TypeScript |
| Shared DB schema | Drizzle ORM (packages/stratus) |
| Shared types | Zod schemas (packages/types) |
| Databases | PostgreSQL (metadata), ClickHouse (events/timeseries) |
| Queue | Redis + BullMQ |
| SDK | Java (external, sends data to Ingest API) |
| Infra | Docker |

---

## Data Flow

```
Java SDK (plugin/mod/server)
  → POST /api/v1/e/:projectId  (Ingest API — influx, Hono)
    → validate API key (PostgreSQL lookup)
    → push to Redis Queue (BullMQ)
    → return 202 Accepted immediately

Redis Queue
  → Worker (cinder) picks up jobs
    → GeoIP lookup (if IP present)
    → validate/enrich event data
    → write raw events → ClickHouse
    → update aggregates → PostgreSQL

Frontend (meridian, Nuxt)
  → query PostgreSQL for metadata/aggregates
  → query ClickHouse for timeseries charts
```

### Event Types (Zod schemas to create)

#### Heartbeat (sent every ~5 minutes)
```typescript
HeartbeatSchema = z.object({
  type: z.literal("heartbeat"),
  timestamp: z.number(),
  server: z.object({
    online: z.number(),
    max: z.number(),
    tps: z.number(),
    mspt: z.number(),
    memory_used_mb: z.number(),
    memory_max_mb: z.number(),
    version: z.string(),      // e.g. "1.21.1"
    software: z.string(),     // e.g. "Paper", "Spigot", "Fabric", etc.
  }),
  plugins: z.array(z.object({
    name: z.string(),
    version: z.string(),
    enabled: z.boolean(),
  })),
})
```

#### Player Event (join/quit/etc)
```typescript
PlayerEventSchema = z.object({
  type: z.literal("event"),
  timestamp: z.number(),
  event: z.enum(["player_join", "player_quit"]),
  payload: z.object({
    player_uuid: z.string().uuid(),
    client_version: z.string(),
    ip_hash: z.string().optional(),   // hashed on SDK side, never raw IP
  }),
})
```

#### Error Event (like Sentry)
```typescript
ErrorEventSchema = z.object({
  type: z.literal("error"),
  timestamp: z.number(),
  plugin: z.string(),
  error: z.object({
    message: z.string(),
    stacktrace: z.string(),
    level: z.enum(["warning", "error", "fatal"]).default("error"),
  }),
})
```

#### Custom Metric
```typescript
CustomMetricSchema = z.object({
  type: z.literal("metric"),
  timestamp: z.number(),
  name: z.string(),
  value: z.number(),
  labels: z.record(z.string()).optional(),
})
```

#### Batch Payload (SDK always batches)
```typescript
IngestBatchSchema = z.array(
  z.discriminatedUnion("type", [
    HeartbeatSchema,
    PlayerEventSchema,
    ErrorEventSchema,
    CustomMetricSchema,
  ])
)
```

## apps/influx — Hono Ingest API

### Endpoints

```
POST /api/v1/e/:projectId          ← main batch ingestion
POST /api/v1/e/:projectId/error    ← error-only endpoint (optional)
GET  /health                       ← healthcheck
```

### Auth Middleware
- Read `X-API-Key` header
- Look up in PostgreSQL `dsn_tokens.key` (check `revoked = false`)
- Attach `projectId` to context, update `lastUsedAt`
- Return 401 if invalid or revoked

### Request handling
1. Parse JSON body as array (or wrap single object in array)
2. Basic structure check only — no heavy validation here
3. Add `receivedAt` timestamp and `projectId` to each event
4. Push entire batch to Redis queue via BullMQ `addBulk()`
5. Return `202 Accepted` immediately

### Rate Limiting
- Per `api_key`: max 100 requests/minute
- Use Redis for rate limit counters

### IP handling
- Extract `X-Forwarded-For` or `req.ip`
- Pass raw IP to worker (worker does GeoIP, then discards IP)
- Never log or store raw IP

## apps/cinder — BullMQ Worker

### Queues

```
ingest-queue    ← all events from influx
```

### Job Processing Steps

1. **Validate** — run full Zod validation on event (reject malformed)
2. **GeoIP** — lookup IP → country_code, then discard IP
3. **Route by event type:**
   - `heartbeat` → upsert `server_metadata`, write to ClickHouse `server_stats`
   - `player_join` → open session in ClickHouse `player_sessions`
   - `player_quit` → close session, write duration
   - `error` → deduplicate by hash(message+stacktrace), upsert `errors` in PostgreSQL
   - `metric` → write to ClickHouse `events`
4. **Write raw event** to ClickHouse `events` table (always, for all types)

### Aggregation Jobs (separate scheduled queue)

Run every 5 minutes via BullMQ repeat:
- Calculate peak online per server per day
- Calculate new vs returning players (first seen = new)
- Calculate avg session duration
- Write results back to PostgreSQL aggregate tables

### Server Route Structure

Routes are split into versioned namespaces to keep concerns separate:

```
server/
├── api/
│   ├── auth/
│   │   └── [...all].ts              ← Better Auth handler (untouched)
│   │
│   ├── v2/                          ← existing downloads/releases API (unchanged)
│   │   ├── projects.get.ts
│   │   └── projects/
│   │       └── [project].get.ts
│   │           └── versions.get.ts
│   │               └── [version].get.ts
│   │                   └── builds.get.ts
│   │                       ├── latest.get.ts
│   │                       ├── [upload.post].ts
│   │                       └── [build].get.ts
│   │
│   └── v3/                          ← new analytics API (stats platform)
│       ├── projects/
│       │   ├── index.get.ts         GET  /api/v3/projects
│       │   ├── index.post.ts        POST /api/v3/projects
│       │   └── [id]/
│       │       ├── stats.get.ts     GET  /api/v3/projects/:id/stats
│       │       ├── players.get.ts   GET  /api/v3/projects/:id/players
│       │       ├── errors.get.ts    GET  /api/v3/projects/:id/errors
│       │       └── tokens/
│       │           ├── index.get.ts    GET  /api/v3/projects/:id/tokens
│       │           ├── index.post.ts   POST /api/v3/projects/:id/tokens
│       │           └── [tokenId].delete.ts
```

**Reasoning:** `/api/auth` stays untouched as Better Auth expects it at that exact path. `/api/v2` keeps the existing downloads API as-is. `/api/v3` is the new analytics namespace — clean separation with no naming collisions, and easy to deprecate/version independently.

## Java SDK (external, not in monorepo)

> This is consumed by plugin developers. Document the interface clearly.

### Initialization
```java
StatClient client = StatClient.builder()
    .dsn("https://TOKEN@ingest.domain.com/api/v1/PROJECT_ID")
    .flushInterval(Duration.ofMinutes(5))
    .build();
```

### SDK Responsibilities
- Parse DSN → extract endpoint + API key
- Buffer events in memory
- Flush buffer every N minutes (configurable)
- Send as single POST with JSON array body
- Hash player IPs client-side before sending (SHA-256, no raw IPs leave server)
- Retry on 5xx with exponential backoff
- Never block the main thread (async flush)

### Headers sent with every request
```
X-API-Key: TOKEN
Content-Type: application/json
User-Agent: StatSDK-Java/1.0.0
```

## Implementation Order

1. `packages/types` — all Zod schemas first, everything depends on this
2. `packages/stratus` — remaining Drizzle tables (server_metadata, plugin_installations, errors)
3. ClickHouse table definitions (migrations)
4. `apps/influx` — Hono API (auth middleware + queue push)
5. `apps/cinder` — BullMQ processor (validate → GeoIP → write)
6. `infra/docker` — docker-compose for local dev
7. `apps/meridian` — Nuxt frontend (analytics dashboard + charts)
8. Java SDK — after API is stable

## Key Design Decisions

- **Ingest always returns 202** — fire and forget, SDK doesn't wait for processing
- **Batch everything** — SDK sends arrays, ingest pushes arrays to queue
- **No raw IPs stored** — GeoIP in cinder, IP discarded after lookup, or hash on SDK side
- **ClickHouse for timeseries** — all charts/graphs query ClickHouse, not PostgreSQL
- **PostgreSQL for metadata** — users, projects, DSN tokens, error deduplication
- **Worker is I/O bound** — Node.js + BullMQ is sufficient, no need for Rust/Go
- **Multi-token DSN** — projects support multiple named DSN tokens (with revocation), not a single api_key
- **Versioned API namespaces** — `/api/v2` (downloads), `/api/v3` (analytics), `/api/auth` (Better Auth) stay fully isolated
