title: Relocation
description: Move libraries into your plugin's package so they never clash with other versions.
---

Relocation renames the packages of a library, for example `com.google.gson` to `com.example.libs.gson`. A server loads classes by name, so two plugins that bring the same library in different versions, or a plugin and a server that both ship it, can step on each other. A relocated copy has its own name and can't clash.

## Why Relocate?

Plugin class loaders ask the server first. If the server ships Gson 2.10 and your plugin loads Gson 2.11 in the same package, your plugin gets the server's 2.10, whatever Quark downloaded.

Quark notices this after loading and warns:

```txt
com.google.code.gson:gson:2.11.0 is not used: com.google.gson.Gson is loaded from
/server/libraries/gson-2.10.1.jar instead, which probably ships another version.
Relocate it to use the version of this plugin: quark("com.google.code.gson:gson:2.11.0") { relocate = true }
in Gradle, or relocate("com.google.gson", ...)
```

Libraries that commonly clash: Gson, Guava, SnakeYAML, Adventure, Netty, SLF4J, Apache Commons, database drivers.

## With the Gradle Plugin

Mark the dependency with `relocate = true` and Quark relocates it in your jar and at runtime:

::code-group
```kotlin [Gradle Kotlin]
import org.bxteam.quark.gradle.relocate

dependencies {
    quark("com.google.code.gson:gson:2.11.0") { relocate = true }
}
```
```groovy [Gradle Groovy]
dependencies {
    quark('com.google.code.gson:gson:2.11.0') { ext.relocate = true }
}
```
::

Or write the rule yourself with `quark { relocate("com.google.gson", "com.example.libs.gson") }`. Both are described in [Gradle Plugin → Relocation](/docs/quark/gradle-plugin/configuration#relocation).

You keep writing `import com.google.gson.Gson;`. Shadow rewrites your classes to the new package when the jar is built, and Quark relocates the downloaded library to the same package when the plugin starts, so both sides meet.

## By Hand

Without the Gradle plugin, pass relocations when you load:

```java
List<Dependency> dependencies = List.of(
        Dependency.of("com.google.code.gson", "gson", "2.11.0")
);
List<Relocation> relocations = List.of(
        Relocation.of("com.google.gson", "com.example.libs.gson")
);

libraryManager.loadDependencies(dependencies, relocations);
```

Your own classes must be relocated to the same package too (with the Shadow or Maven Shade plugin), otherwise they keep looking for `com.google.gson`.

::callout{type="warn" title="Package names in strings"}
  Shadow rewrites string literals that look like a relocated class name. If you build a package name at runtime, derive it from a class (`Gson.class.getPackageName()`) instead of writing it out.
::

### Relocation API

```java
Relocation relocation = Relocation.of("com.google.gson", "com.example.libs.gson");

// or with the builder
Relocation same = Relocation.builder()
        .from("com.google.gson")
        .to("com.example.libs.gson")
        .build();

relocation.pattern();          // com.google.gson
relocation.relocatedPattern(); // com.example.libs.gson
relocation.isEffective();      // false if from and to are the same
```

A rule covers the package and all its sub-packages, so `com.google.gson` also moves `com.google.gson.reflect` and `com.google.gson.stream`.

## How It Works

- Quark relocates JARs with its own relocator on top of [ASM](https://asm.ow2.io). ASM is not shipped with Quark: the first relocation downloads `asm` and `asm-commons` 9.10.1 into an isolated class loader, so the plugin jar stays small and the server's ASM doesn't matter.
- Classes (multi-release ones under `META-INF/versions` too) and string constants that name a relocated class are rewritten, `META-INF/services` files are renamed and their entries relocated, other resources move with their package. Signature files are dropped, they would no longer match.
- Relocated JARs are cached next to the original in `<dataDirectory>/libs`, one copy per set of relocations. Changing the rules creates a new copy, the next start reuses it.
