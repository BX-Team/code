title: Signatures and trust
description: How Riven signs releases and decides which key to trust.
---

Releases are signed with ed25519. `riven build` signs every channel pointer and manifest; the installer verifies them before touching a single file.

## Keys

- `riven keygen` creates one key per pack in `<config>/keys/<pack>.ed25519`. Back it up: the Releases page shows the file, and losing it means every player has to accept a new key.
- `riven build` needs the key unless you pass `--unsigned`.
- The public key is written into every channel pointer, so install links stay short and players never paste a key.

## Which key an install trusts

1. **A pinned key.** The first install pins the key the release carries in `trusted.json` (trust on first use). Every later update must be signed with it.
2. **The link's key.** A link can also name the key: `https://example.com/pack/#key=ed25519:…`. Then even the first install refuses a release signed with another key. Riven does not add it to the links it prints; add it yourself where you publish links if you want that.

Once a pack was signed, an unsigned release or a release signed with another key is refused. In the launcher the game then starts with the installed version and the player is asked whether to trust the new key.

## Rotating a key

If you have to change the key, tell your players first. In the launcher they confirm the new key once in the dialog that appears on the next launch; on the command line they reset the pin:

```bash
riven trust reset https://example.com/pack/channels/stable.json
```

The error message names the exact URL to reset.

## Hashes

Signatures protect the manifest; the manifest pins the sha512 of every file. A new — possibly malicious — version of a mod never arrives without the author running `riven update` and publishing a release.
