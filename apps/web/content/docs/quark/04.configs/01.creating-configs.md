`quark-config` turns a plain class into a config file. Fields are keys, field initializers are the defaults and annotations become comments. Add it with `quark { modules(QuarkModule.CONFIG) }`, which also adds the YAML format and, on Paper, Folia and Bukkit, the [Bukkit serializers](/docs/quark/configs/serializers#bukkit-types).

## Config Class

```java
@Header({"MyPlugin configuration", "Wiki: https://example.com/wiki"})
@NameStrategy(NameStyle.HYPHEN_CASE)
public class PluginConfig extends QuarkConfig {
    @Comment("Prefix of every message")
    public String prefix = "<gray>[MyPlugin]</gray> ";

    @Comment("How many homes a player can set")
    public int maxHomes = 3;

    public List<String> disabledWorlds = List.of("world_nether");

    public Database database = new Database();

    @Exclude
    public String runtimeOnly = "not saved";

    public static class Database {
        public String host = "localhost";
        public int port = 3306;

        @CustomKey("user")
        public String username = "root";
    }
}
```

This class produces:

```yaml [config.yml]
# MyPlugin configuration
# Wiki: https://example.com/wiki

# Prefix of every message
prefix: '<gray>[MyPlugin]</gray> '
# How many homes a player can set
max-homes: 3
disabled-worlds:
- world_nether
database:
  host: localhost
  port: 3306
  user: root
```

The class needs a no-argument constructor, which may be private. Every non-static, non-transient field is a key, whatever its visibility. Nested objects are plain classes with a no-argument constructor or records.

## Loading

```java
public final class MyPlugin extends JavaPlugin {
    private PluginConfig config;

    @Override
    public void onEnable() {
        config = QuarkConfig.create(PluginConfig.class, getDataFolder().toPath().resolve("config.yml"));
        config.load();

        getLogger().info("Players can set " + config.maxHomes + " homes");
    }
}
```

`create(...)` only builds the object with its defaults. `load()` reads the file, creating it if it is missing.

| Method | Description |
|--------|-------------|
| `load()` | Reads the file, migrates and validates it, copies the values into the object and writes the file again if it changed |
| `reload()` | The same as `load()`, for reload commands |
| `save()` | Writes the current values to the file |
| `file()` | The file of this config |
| `toNode()` | The values as a [ConfigNode](/docs/quark/configs/migrations#confignode) tree, as they would be saved |

To change a value from code, set the field and call `save()`:

```java
config.maxHomes = 5;
config.save();
```

## How Files Are Written

Quark regenerates the file from the class on every save, the same way [okaeri-configs](https://github.com/OkaeriPoland/okaeri-configs) does:

- keys are in field order and the values from the file are kept;
- missing keys are added with their defaults, so new options appear in old files after an update;
- comments come from `@Header` and `@Comment`. **Comments written by hand are lost**, document options with annotations instead;
- keys no field is bound to (an option you removed, a typo) are kept at the end of their section. Use `removeOrphans()` to delete them.

### All or Nothing

A load either succeeds completely or changes nothing. The file is read into a fresh object, migrated and validated, and only then are the values copied into your config. If anything fails, `load()` throws, your config keeps its previous values and the file is not touched. That makes `reload()` safe: a typo in the file never leaves the plugin half-configured.

Files are written to `config.yml.tmp` first and then moved over the old file, so a crash during save can't leave a broken file behind.

### Errors

| Exception | When |
|-----------|------|
| `ConfigValidationException` | Values failed [validation](/docs/quark/configs/validation). Lists every violation |
| `ConfigException` | The file can't be read, parsed, migrated or written, or a value has the wrong type |

```java
try {
    config.reload();
    sender.sendMessage("Config reloaded");
} catch (ConfigException e) {
    sender.sendMessage("Config not reloaded, old values kept: " + e.getMessage());
}
```

The messages name the file and the key: `Cannot load /plugins/MyPlugin/config.yml: max-homes: 'three' is not a number (int)`.

## Annotations

| Annotation | Target | Description |
|------------|--------|-------------|
| `@Header({...})` | class | Comment lines at the top of the file. An empty string is a blank line |
| `@Comment({...})` | field | Comment lines above the key. An empty string is a blank line |
| `@NameStrategy(NameStyle)` | class | How field names become keys. Nested classes inherit it |
| `@CustomKey("...")` | field | An explicit key for one field |
| `@Exclude` | field | The field is neither loaded nor saved. `static` and `transient` fields are always excluded |
| `@ConfigVersion(n)` | class | The version of the file, see [Migrations](/docs/quark/configs/migrations) |

### Naming Styles

| `NameStyle` | `maxHTTPConnections` becomes |
|-------------|------------------------------|
| `IDENTITY` (default) | `maxHTTPConnections` |
| `HYPHEN_CASE` | `max-http-connections` |
| `SNAKE_CASE` | `max_http_connections` |

## Options

The second form of `create(...)` takes a configurer for everything else:

```java
config = QuarkConfig.create(PluginConfig.class, options -> options
        .file(getDataFolder().toPath().resolve("config.yml"))
        .migrations(Migration.of(1, 2, root -> root.node("prefix").moveTo(root.node("messages", "prefix"))))
        .serdes(registry -> registry.register(Rank.class, new RankSerializer()))
        .validator(new MyValidator())
        .removeOrphans()
        .logger(platform.logger()));
```

| Option | Description |
|--------|-------------|
| `file(Path)` / `file(File)` | **Required.** The config file |
| `migrations(...)` | Steps that upgrade older files, see [Migrations](/docs/quark/configs/migrations) |
| `serdes(...)` | Serializers for your own types, see [Serializers](/docs/quark/configs/serializers) |
| `validator(...)` | Extra validators, see [Validation](/docs/quark/configs/validation#custom-validators) |
| `removeOrphans()` | Deletes keys no field is bound to |
| `format(ConfigFormat)` | Another file format. YAML is found automatically |
| `discover(false)` | Don't pick up the format, serializers and validators of modules on the class path |
| `logger(QuarkLogger)` | Where migrations and skipped modules are reported |

## Multiple Files

Every file is its own class. Messages, GUIs or per-world settings are just more configs:

```java
Path folder = getDataFolder().toPath();
config = QuarkConfig.create(PluginConfig.class, folder.resolve("config.yml"));
messages = QuarkConfig.create(Messages.class, folder.resolve("messages.yml"));

config.load();
messages.load();
```

## YAML Backend

The YAML format (`quark-config-yaml`) runs on [snakeyaml-engine](https://bitbucket.org/snakeyaml/snakeyaml-engine), which Quark does not ship. When the first config loads, Quark looks for it in this order:

1. **On the class path**: you shaded it into the plugin. The Gradle plugin relocates it to `<group>.libs.quark.snakeyaml`.
2. **Downloaded**: if `quark-dependency` is in the plugin, snakeyaml-engine is downloaded into `libs/` next to the config file and relocated to the same package.
3. **Neither**: the load fails and says what to add.

So with `modules(QuarkModule.DEPENDENCY, QuarkModule.CONFIG)` there is nothing to do. With `CONFIG` alone, shade the library:

::code-group
```kotlin [Gradle Kotlin]
dependencies {
    implementation("org.snakeyaml:snakeyaml-engine:3.1.1")
}
```
```groovy [Gradle Groovy]
dependencies {
    implementation 'org.snakeyaml:snakeyaml-engine:3.1.1'
}
```
::

If your plugin already has a library manager, let configs use it, so snakeyaml-engine is added the same way as your other libraries and lands in the same `libs/` folder:

```java
LibraryManager libraryManager = LibraryManager.builder()
        .plugin(this)
        .dataDirectory(getDataFolder().toPath())
        .build();
libraryManager.loadFromGradle();
BackendProvider.libraryManager(libraryManager);
```
